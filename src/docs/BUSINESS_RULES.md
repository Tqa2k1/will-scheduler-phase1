> 2026-08 に確定した業務ルール指示（`docs/AUTO_ASSIGN_RULES.md` のもとになった要件）から

> AUTO_ASSIGN_RULES.md に分離しているので、そちらも合わせて読むこと。

## 用語（業務コード）

| コード (DB `CartPosition.code`) | 名称 | 分類 |
|---|---|---|
| `A` | Aカート（業務A） | CART |
| `B` | Bカート（業務B） | CART |
| `全` | 全カート（業務全） | CART |
| `BF` | BF | SPECIAL |
| `BREAK` | 休憩 | SPECIAL |
| `MOVE` | 移動 | SPECIAL |
| `WHILL_ARRIVAL_PREP` | WHILL到着準備 | SPECIAL |
| `WHILL_ARRIVAL_CLEANUP` | WHILL到着片づけ | SPECIAL |
| `WHILL_DEPARTURE_PREP` | WHILL出発準備 | SPECIAL |

（出典: `prisma/seed.ts` の `positions` 配列。これが実際にDBへ投入される業務マスタ。）

## 業務A・業務B・業務全

- 業務A: 稼働時間 **5:00〜26:00（=翌2:00）**。
- 業務B: 稼働時間 **6:00〜24:00**。
- 業務全: 稼働時間 **5:00〜25:00（=翌1:00）**。
- 時間帯あたりの必要人数は `TaskRequirement.requiredCount`（管理画面 `/tasks` で設定）で決まる。
  未設定の場合、自動アサインのフォールバック値は1名（`src/lib/autoAssign.ts` の `capFor`）。
  ただし `prisma/seed.ts` は初回投入時にA/B/全それぞれ requiredCount=4 をデフォルトとして
  設定している（⚠️ 要確認: 実運用でこの値が「1名」相当を想定しているのか「4名（4台のカート）」を
  想定しているのかはDB/管理画面側の設定次第であり、コードからは断定できない）。
- 優先順位は 業務A > 業務B > 業務全 > WHILL関連業務 > 休憩 > 事務時間（AUTO_ASSIGN_RULES.md参照）。

## WHILL関連業務

固定の時刻・固定の必要人数を持つ、1日4つのイベント（`src/lib/autoAssign.ts` の `WHILL_EVENTS`）。

| 業務 | 時間 | 必要人数 |
|---|---|---|
| WHILL（到）片づけ | 10:00〜11:00 | 1名 |
| WHILL（出）準備 | 11:00〜12:00 | 2名 |
| WHILL（出）片づけ | 18:00〜19:00 | 2名 |
| WHILL（到）準備 | 19:00〜20:00 | 1名 |

- パートスタッフ（`EmployeeRole.PARTTIME`）はWHILL業務に配置禁止。
- WHILL業務のために業務A/B/全の人員を削らない（優先順位が低いため、A/B/全に必要な人を
  奪ってはいけない）。

## 明け番（夜勤引き継ぎ）

- `ShiftType` の `明番`（22:00〜08:00, `spansMidnight: true`）で勤務するスタッフ。
- 当日シート上では、前日から続く夜勤として **4:00〜シフト終了時刻** の部分だけが
  「引き継ぎ（`isCarryOver: true`）」として表示される（`src/lib/dailyRoster.ts`）。
- 休憩は **2時間連続**。ただし全員を同時に休憩へ入れない。業務A/B/全の稼働時間内では、
  他スタッフの配置状況を見ながら順番に休憩を設定する（業務A/B/全の稼働時間外はこの制限なし）。

## 休憩ルール（通常勤務）

- 4時間未満の勤務には休憩を配置しない。
- 4時間以上勤務した場合、勤務開始から **3〜5時間程度** を目安に休憩を配置する。
- スタッフ全員を同時に休憩に入れない（時間をずらす）。
- 休憩よりも業務A/B/全の運営を優先する＝休憩によって業務A/B/全の枠が空白になるくらいなら、
  休憩の配置を後回しにする。

## 事務時間（OFFICE）

- **最初から事務時間を配置しない。** 業務A/B/全・WHILL関連業務・休憩をすべて配置したあとに
  余った時間だけを使う。
- パートスタッフは事務時間に配置禁止。

## パートスタッフ（`EmployeeRole.PARTTIME`）のルール

- 配置可能: 業務A / 業務B / 業務全（乗車業務のみ）。
- 配置禁止: WHILL準備・WHILL片づけ・事務時間・その他業務。
- 勤務時間の上限: **週20時間**（`src/lib/weeklyHours.ts` の `PARTTIME_WEEKLY_HOUR_LIMIT`）。
  この上限は既存のプロジェクトルールであり、今回の業務ルール改訂でも変更していない。

## 日別スケジュール画面の表示ルール

- 表示列: 社員名 / 勤務時間 / 業務内容 / 配置状況（+ その他既存表示項目）。**「シフト」列は
  表示しない**（2026-08改訂で削除。`ShiftType`のDBデータ・ロジック自体は削除していない）。
- 社員の表示順は役割（role/yakuwari）で決めない。
  ① 勤務開始時刻が早い順 → ② 同じ場合は勤務終了時刻が早い順 → ③ それでも同じ場合は氏名（かな順）。
- 配置状況（不足表示）は、業務A/B/全に加えてWHILL関連業務も対象にし、各業務**自身の稼働時間内
  のみ**で必要人数と実際配置人数を比較する（稼働時間外・誰も勤務していない時間帯は不足表示しない）。

## 1日の人員体制（12人＝早番/遅番/明番 各4人。2026-08追加）

「業務A/B/全/WHILL」（1時間粒度の業務充足）とは別に、1日の人員体制として以下の3ダイヤ
それぞれ4人、合計12人を基準とする（`src/lib/shiftWindowStaffing.ts`）。

| ダイヤ | 時間 | 必要人数 |
|---|---|---|
| 早番 | 08:00〜17:00 | 4名 |
| 遅番 | 13:00〜22:00 | 4名 |
| 明番 | 22:00〜翌08:00 | 4名 |

- 3ダイヤは既存の`ShiftType`マスタ（早番/遅番/明番）と完全に一致する。
- 明番（22:00〜翌8:00）は**1つの連続勤務**として扱う。`MonthRoster`は開始日（22:00側の日付）に
  対して1レコードのみ存在するため、日をまたいでも二重カウントされない。
- 必要人数（4名×3ダイヤ）は現状コード内の固定値。管理画面からの変更には対応していない。

## シフト調整・希望勤務（KIBO）（2026-08追加）

- 上記の人員体制（早番/遅番/明番 各4名）に対して不足が出ている場合、管理者は「シフト調整」画面
  から、出勤できそうな従業員へ希望勤務(KIBO)登録を促すメールを送信できる。
- 従業員はメールを受け取っても**Gmailに直接返信する必要はない**。システムにログインし、
  「勤務希望申請」画面から日付・希望ダイヤを選んでKIBO登録する。
- KIBOは**あくまで希望の登録**であり、登録しただけでは勤務確定にはならない。管理者が
  内容を確認し、承認（確定）または却下する。承認されると、対応するシフト種別
  （早番/遅番/明番）が月間勤務表に反映される。
- KIBO登録の受付期間: **翌月分のみ・当月10日まで**。11日以降はその月の受付を締め切る
  （既存プロジェクトにこの締切ルールはなかったため、2026-08の要件で新規に追加した）。
- 送信対象の絞り込み条件: 有効な従業員・連絡先メールが設定済み・その日まだ出勤予定でない・
  その日にNG設定（`PersonalConstraint`）がない・同じダイヤに既にKIBO登録済みでない。

## 従業員個人の優先順位（2026-08追加。既存の「役割優先順位」を補完）

- 既存の「役割優先順位」（`RolePriority`。正社員/契約社員/バイト等の**役割単位**の優先順位。
  自動アサインで使用）に加えて、**同じ役割の中での個人単位の優先順位**を設定できる。
- 例: 正社員グループの中で「山田さん→佐藤さん→田中さん」のように並べる。
- 用途は「ある時間帯で人員が不足したとき、同じ役割の中でどの従業員を優先的に検討するか」
  （シフト調整のメール送信対象の並び順）**のみ**。担当業務（A/B/全/WHILL・事務時間等）の
  決定には使わない。
- 判定の流れ: 「時間帯が不足 → その時間に出勤可能な人を確認 → 既存のルール（NG設定・
  週の勤務時間上限など）を確認 → 従業員個人優先順位の高い人を優先」という順序。
  優先順位が高い人がその時間に対応できない場合は、次の優先順位の人を検討する。

## 業務の時間単位（30分対応。2026-08追加）

- 業務（`CartPosition`）は基本的に**1時間単位**（`slotUnitMinutes = 60`）のまま。既存の
  全業務はこの設定のまま変更していない。
- 管理画面で個別に「30分も可」に設定した業務のみ、日別スケジュールの手動編集画面で
  **30分単位のコマ**として配置できる。
- 日別スケジュール画面のタイムライン表示自体は**30分刻み**に変更したが、これは表示・手動編集の
  粒度を細かくしただけであり、**自動アサイン（`autoAssign.ts`）は引き続き1時間単位のまま**
  （今回のスコープ外。既存の自動アサインロジックは変更していない）。

## 持ち場交代ルール

- 業務A/B/全について、同じスタッフが長時間同じ持ち場を担当し続けないようにする。
- 目安: **1〜3時間程度**で担当を交代する。

## ロールと権限（勤務系ロールとログイン系ロールは別軸）

- `EmployeeRole`（従業員としての役割）: `STAFF`（社員）/ `CONTRACT`（契約社員）/
  `PARTTIME`（バイト）/ `OJT` / `INC`（現状未使用、将来拡張用）。
- `UserRole`（ログインアカウントの権限）: `ADMIN` / `INC` / `EMPLOYEE`。
  `EmployeeRole.INC` と `UserRole.INC` は名前が同じだが別のenumであることに注意。

## ⚠️ 未確認・要確認事項

- WHILL業務の「到（到着）」「出（出発）」がそれぞれ何を指すか（WHILLの到着便・出発便の対応と
  推測されるが、業務仕様書等の一次情報での確認はできていない）。
- `RolePriority`（自動バックフィル時の優先順位: INC→STAFF→CONTRACT→PARTTIME→OJT）と、
  今回のAUTO_ASSIGN_RULES.mdの優先順位（A→B→全→WHILL→休憩→事務時間）は「何を優先するか」の
  軸が異なる（前者は「誰を優先するか」、後者は「どの業務を優先するか」）。両者は独立したルールとして
  共存している。
